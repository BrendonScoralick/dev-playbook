Fluxo e Glossário

Desenvolvimento de software assistido por IA, do PRD à operação. Exemplos usam o sistema de inscrição em workshops (dados fictícios).

1. O ciclo completo

Cada fase termina num gate (ponto de aprovação). A Spec, versionada no repositório, é a fonte da verdade, e o ciclo fecha: o que a operação aprende vira uma nova Spec.

Duas rotas para o começo (detalhes em metodo/fluxo/ciclo.md):
Rota B, protótipo primeiro (a habitual): Brief de 5 linhas → Protótipo no Claude Design (3 prompts) → PRD gerado no fechamento e revisado à mão → Spec.
Rota A, PRD primeiro: o desenho abaixo, quando o problema e as regras já chegam definidos.
1. PRDPor que e para quem? Hipótese + métrica (1 página)"Organizadores perdem vagas controlando inscrições em planilha."
↓
GATE: problema e métrica aprovados
↓
2. DiscoveryIsso é verdade? Validar antes de construirConversar com 3 organizadores.
↓
GATE: hipótese confirmada
↓
3. Design + handoff (Claude Design)Telas com todos os estados: vazio, erro, sem permissão, carregandoLista de workshops, tela "vagas esgotadas". O handoff é insumo da Spec, não atalho.
↓
GATE: telas e inventário aprovados
↓
4. Spec + threat modelCritérios EARS, STRIDE, matriz perfil × recurso × ação. Vai em PR só de documentação."QUANDO um usuário enviar DELETE para inscrição que não é dele, O SISTEMA DEVE responder 403."
↓
GATE: PR da Spec aprovado (Code Owners)
↓
5. Plano de tarefasTarefas pequenas, cada uma ligada a um critério da SpecT1 tabela de inscrições; T2 rota POST; T3 regra de vagas.
↓
6. Red: testes primeiroTestes falhando pelo motivo certo, incluindo testes de abuso. PR rascunho (CI vermelho de propósito)Teste "inscrição nº 31 deve ser recusada" falha com "esperado erro, recebido sucesso".
↓
GATE: testes revisados, falhando pelo motivo certo
↓
7. Green + Refactor: implementaçãoCódigo mínimo para passar; depois limpar sem mudar o comportamento. Claude Code conduzido por você. Nunca alterar teste para fazê-lo passar.
↓
8. Pull Request + CILint, tipos, testes, varredura de segredos; leitura do diff; aprovação
↓
GATE: CI verde + aprovação (autor não aprova o próprio PR)
↓
9. Release (CD)Squash and merge na main e deploy
↓
10. OperaçãoMonitorar, backup testado, runbook. Em incidente: conter primeiro, investigar depois
↓
11. FeedbackPostmortem, métricas, pedidos de usuários"Faltava a regra de workshop lotado."
↺ Volta à fase 4: nova regra na Spec → teste → correção
Modo rápido (mudança pequena e de baixo risco, ex.: trocar um texto): spec curta + teste, sem as fases 1 a 3. Não vale para autenticação, permissões, dados pessoais ou migrações.

3. Glossário

Fluxo e método
Gate
Ponto de aprovação no fim de uma fase. Só se avança com um "ok". Ex.: a gestora aprova a Spec antes de qualquer código.
PRD
Documento do "porquê": problema, público, hipótese e métrica de sucesso. Ex.: "reduzir inscrições perdidas de 15% para 2%".
Discovery
Fase de verificar se o problema é real antes de construir.
Handoff
Entrega do design para o desenvolvimento (telas, estados, textos). Fica em pasta somente leitura e versionada; alimenta a Spec.
Spec (especificação)
Documento do "o quê, exatamente": regras e critérios de aceite, versionado no repositório. Fonte da verdade.
EARS
Formato de escrever requisitos: "QUANDO [evento], O SISTEMA DEVE [resposta]". Força a regra a ser testável.
Critério de aceite
Condição objetiva que diz se a funcionalidade está pronta. Todo critério vira teste. Ex.: workshop sem vagas recusa a inscrição.
Critério negativo
Critério que diz o que o sistema deve impedir. Ex.: usuário não pode cancelar a inscrição de outro.
Threat model
Mapa do que pode dar errado (ataques e abusos) antes de programar.
STRIDE
Checklist de 6 ameaças: falsificação de identidade, adulteração de dados, repúdio, vazamento de informação, negação de serviço e elevação de privilégio.
Matriz perfil × recurso × ação
Tabela de quem pode fazer o quê com cada coisa. Ex.: participante pode ler e cancelar a própria inscrição; não pode ler a de outros.
ADR
Registro curto de uma decisão grande de arquitetura e do porquê.
SDD
Spec-Driven Development: a Spec guia o código. Prática consolidada, não padrão oficial.
TDD
Test-Driven Development: escrever o teste antes do código.
Red / Green / Refactor
Red: teste falhando pelo motivo certo. Green: código mínimo para passar. Refactor: limpar sem mudar o comportamento.
Falhar pelo motivo certo
O teste falha porque o comportamento está errado ("esperado 403, recebido 200"), não porque o teste está quebrado ("módulo não encontrado").
Teste de abuso (abuse case)
Teste que tenta fazer o que um atacante faria. Ex.: apagar a inscrição de outra pessoa.
Modo rápido
Fluxo enxuto para mudanças pequenas e de baixo risco: spec curta + teste.
AGENTS.md / constitution
Arquivos com regras permanentes para a IA seguir em todo o projeto.
Spec Kit
Ferramenta do GitHub para trabalhar com Spec Driven Development.
Git e GitHub
Repositório
Pasta do projeto com o histórico guardado pelo Git (na pasta oculta .git).
Branch
Cópia paralela do código para trabalhar sem mexer na versão oficial. Ex.: spec/inscricao-workshop.
main
Branch oficial. Protegida: só recebe mudanças via PR aprovado.
Commit
"Foto" das mudanças, guardada no seu computador, com descrição. Não envia nada.
Hash
Identificador único de um commit. Ex.: 4cac5aa.
Staging (área de espera)
Onde o git add deixa o que entrará no próximo commit.
Working tree clean
Sem mudanças pendentes.
Push / Pull
Push envia commits ao GitHub; pull traz do GitHub para o local.
Pull Request (PR)
Pedido para incorporar sua branch na main, com espaço para revisão e comentários. O PR é o pedido; o merge é a ação.
PR rascunho (draft)
PR ainda não pronto para merge. Usado no Red, com CI vermelho de propósito.
Merge / Squash and merge
Merge incorpora a branch na main. Squash junta todos os commits do PR em um só, deixando o histórico limpo.
Diff
Comparação do antes e depois de um arquivo. É o que você lê para revisar o que a IA entregou.
Proteção da main
Regras do GitHub: exige PR, CI verde e aprovação. Depende do plano do GitHub; confirmar antes de afirmar.
CODEOWNERS
Arquivo que define quem deve aprovar mudanças em cada área. Cobre só áreas sensíveis (specs, ADRs, auth, permissões, migrações, CI).
Conventional Commits
Padrão de prefixo na mensagem do commit: feat, fix, docs, test.
Qualidade e entrega
CI (integração contínua)
Robô que, a cada PR, roda lint, tipos, testes e varredura de segredos.
CD / Release
Entrega automatizada do código aprovado para produção.
Lint
Verificador automático de estilo e erros comuns no código.
GitHub Actions
Ferramenta do GitHub que executa o CI.
Docker Compose
Sobe o sistema e o banco na sua máquina de forma igual para todo o time.
Teste unitário / de integração / E2E
Unitário testa uma peça; integração testa peças juntas (ex.: rota + banco); E2E simula o usuário no navegador.
Segurança
Autenticação vs autorização
Autenticação: quem é você? Autorização: o que você pode fazer? Ex.: logar é autenticação; cancelar só a própria inscrição é autorização.
Guard
Trecho do back-end que barra requisições sem permissão. A autorização real mora aqui, não no front-end nem no proxy do Next.js.
OWASP Top 10
Lista das falhas de segurança web mais comuns.
IDOR
Acessar o dado de outro trocando o ID na URL ou na chamada da API. A correção é verificar o dono no servidor; UUID só dificulta adivinhar, não protege.
Mass assignment
O sistema aceita campos que o usuário não deveria enviar. Ex.: enviar "perfil":"admin" ao se inscrever.
Injection
Entrada do usuário interpretada como comando (ex.: SQL). Defesa: consultas parametrizadas e validação.
XSS
Script malicioso injetado em uma página e executado no navegador de outro usuário.
CSRF
Site malicioso faz o navegador do usuário logado enviar uma ação sem ele querer.
CORS
Regra do navegador sobre quais sites podem chamar sua API. Configuração frouxa demais é risco.
Open redirect
Link do seu site que redireciona para um endereço externo controlado pelo atacante.
Rate limiting
Limite de tentativas por tempo. Freia força bruta e abuso.
Cookie HttpOnly
Cookie que o JavaScript da página não consegue ler, reduzindo o roubo de sessão por XSS.
Token curto + refresh rotativo
Credencial de sessão que expira rápido, renovada por outra que é trocada a cada uso.
Argon2id / bcrypt
Algoritmos para guardar senhas como hash. Nunca guardar a senha em texto. O bcrypt tem limite de 72 bytes.
Supply chain
Risco nas bibliotecas de terceiros que o projeto usa. Mitigação: versões corrigidas, revisão de dependências.
CVE
Código público de uma vulnerabilidade conhecida. Confira sempre se a versão usada tem correção.
Segredo
Senha, chave de API ou token. Nunca vai no código nem num prompt; o CI procura vazamentos.
LGPD
Lei brasileira de proteção de dados. CPF é dado pessoal: sem logs, com máscara e prazo de retenção.
Operação
Contenção
Primeira ação num incidente: parar o estrago (desativar a rota, restaurar o dado) antes de investigar.
Runbook
Roteiro passo a passo de o que fazer quando algo específico quebra.
Postmortem
Relato curto de um incidente: o que houve, a causa e o que mudaremos. Foca no processo, não em culpados.
SLO
Meta de qualidade do serviço. Ex.: 99,5% das inscrições concluídas em até 2 segundos. Formalizar só depois do MVP.
Backup testado
Cópia dos dados que já foi restaurada ao menos uma vez para provar que funciona.
Feedback loop
Aprendizado da operação voltando para a Spec: bug → Spec → teste → correção.
